# Bot API research for current upstream T3 Code

Implementation update, 2026-10-02: the bot uses the WebSocket turn-start bootstrap for T3-managed worktree paths, branch creation, and setup. Upstream main requires `destinationPath` for `projectClone.start`, so the bot supplies `<t3.cloneRoot>/<owner>/<repo>` to that method. T3 performs the clone and registers the project; the bot waits for completion and uses T3's returned checkout path. There is no worktree root setting.

Researched 2026-10-01 against `pingdotgg/t3code` upstream main commit `5cc99e1c23980d7995a13c47f969b47cb68ed1be`. All implementation claims below refer to that commit. The local Pulse fork and installed server are outside this report. No running server or application state was accessed.

## Result

The server already implements the operations needed to register a repository, create a separate worktree and durable thread, and start an agent with a collected prompt. A bot can call these APIs without opening the GUI. The bot must supply Discord/Linear context and routing itself. The implementation has both typed Effect WebSocket RPCs and HTTP orchestration reads/dispatch. It also has a dedicated asynchronous clone-backed project API. Sources: [clone-backed project handler](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/ws.ts#L3256), [turn bootstrap schema](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/packages/contracts/src/orchestration.ts#L1292), [HTTP orchestration contracts](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/packages/contracts/src/environmentHttp.ts#L508).

## Smallest supported flow

1. Resolve the bot's configured repository to an existing environment-local project ID and workspace root.
2. For a new repository, call `projectClone.start` using an absolute destination beneath the bot's configured root and subscribe to clone progress. Proceed only after completion. For an existing checkout lacking a project record, dispatch `project.create`.
3. Send one WebSocket `orchestration.dispatchCommand` carrying a `thread.turn.start` command with `bootstrap.createThread` and `bootstrap.prepareWorktree`, plus `bootstrap.runSetupScript` when repository setup should run.
4. Subscribe to the durable thread and setup progress. Save the thread ID and sequence in the bot's own job record.

The bootstrap schema is:

```ts
bootstrap: {
  createThread: {
    projectId, title, modelSelection, runtimeMode, interactionMode,
    branch: null, worktreePath: null, createdAt
  },
  prepareWorktree: {
    projectCwd, baseBranch,
    branch,                 // optional new branch name
    startFromOrigin: true,  // optional fetch before branching
    requireWorktree: true   // fail instead of using the main checkout
  },
  runSetupScript: true
}
```

This is implemented server behavior, not a proposed endpoint. Bootstrap validates the repository and base commit, optionally fetches origin, creates the thread and persists its first user message, creates the worktree, updates the thread's branch/path, runs setup, then dispatches the turn. `requireWorktree:true` is useful for this bot: without it, an invalid repository or empty base can fall back to working in the project checkout. Sources: [bootstrap schema](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/packages/contracts/src/orchestration.ts#L1292), [validation and fallback](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/ws.ts#L1335), [thread creation and early message persistence](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/ws.ts#L1427), [worktree creation](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/ws.ts#L1503), [metadata and agent handoff](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/ws.ts#L1590).

Clone registration happens before Git finishes. The server rejects explicit thread creation and bootstrap turn starts for tracked projects whose clone is running, failed, or cancelled. Do not treat the clone start response as readiness. Source: [start and registration](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/project/ProjectCloneTracker.ts#L262), [dispatch guard](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/project/ProjectCloneTracker.ts#L444).

HTTP and WebSocket dispatch have different implementations. The HTTP handler normalizes the command and calls the orchestration engine directly; the combined worktree/thread/setup bootstrap runs in the WebSocket handler. Use WebSocket dispatch for `bootstrap`. HTTP can dispatch explicit `project.create`, `thread.create`, and a turn on an existing thread, after the worktree has been prepared. The shared input schema alone does not prove bootstrap parity. Sources: [HTTP handler](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/orchestration/http.ts#L97), [WebSocket bootstrap routing](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/ws.ts#L1921).

## Paths and credentials

Clone destination is an explicit server-local path. The clone service resolves it, expands home notation, rejects nonempty destinations, and creates missing parent directories. There is no bot-specific configured clone root in that input or containment check in that implementation. Choosing and validating the bot's allowed root is a recommendation for the integration, not existing server enforcement. Sources: [destination contract](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/packages/contracts/src/sourceControl.ts#L72), [destination handling](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/sourceControl/SourceControlRepositoryService.ts#L196).

Provide `provider:"github",repository:"owner/repo"` for provider-assisted URL lookup, or `remoteUrl` for a direct clone. `protocol` supports `auto`, `ssh`, `https`. Git runs on the environment host and needs credentials available there. Discord and Linear credentials do not grant repository access. Sources: [provider lookup versus remote URL](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/sourceControl/SourceControlRepositoryService.ts#L247), [Git subprocess invocation](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/sourceControl/SourceControlRepositoryService.ts#L302), [clone protocols](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/packages/contracts/src/sourceControl.ts#L54).

For an explicit custom worktree directory use `vcs.createWorktree` with `path`, followed by `thread.create` and `thread.turn.start`. Bootstrap exposes base/branch controls but no worktree path override. Source: [explicit path](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/packages/contracts/src/git.ts#L140), [bootstrap worktree fields](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/packages/contracts/src/orchestration.ts#L1303).

## Progress, durability, and retries

Orchestration commands persist events and accepted/rejected command receipts. A repeated accepted `commandId` returns the saved sequence for the same aggregate. A receipt proves command handling, not completed provider work. Observe session/turn events or the resulting thread snapshot for agent outcome. Source: [receipt lookup and aggregate check](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/orchestration/Layers/OrchestrationEngine.ts#L144), [transactional event and receipt persistence](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/orchestration/Layers/OrchestrationEngine.ts#L274), [dispatch response](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/packages/contracts/src/orchestration.ts#L2267).

Clone and bootstrap add side effects outside that command transaction. `projectClone.start` has no caller command ID and tracks duplicate project/destination claims only in memory. Treat the integration as a resumable job: persist repository, chosen path, project/thread/message/command IDs, and completed steps; after ambiguous failures, reconcile before retrying. This job record is a recommendation, not an upstream bot API. Sources: [clone start has no commandId](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/packages/contracts/src/projectClone.ts#L60), [clone claims](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/project/ProjectCloneTracker.ts#L280), [bootstrap subcommands](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/ws.ts#L1427).

Background clone and tracked worktree bootstrap survive a dropped client socket. They are not durable jobs across server restart. Clone progress exists in memory and a server restart forgets it; the durable project can remain with an incomplete checkout. Worktree live progress also exists in memory, while `worktree-setup` activity stores the latest recorded state in the durable thread. Sources: [clone lifecycle](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/project/ProjectCloneTracker.ts#L36), [restart limitation](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/packages/contracts/src/projectClone.ts#L10), [detached bootstrap lifetime](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/ws.ts#L1751), [live tracker](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/packages/contracts/src/worktreeSetup.ts#L5), [persisted setup activity](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/packages/contracts/src/worktreeSetup.ts#L74).

Setup is best effort. Tracked bootstrap observes a shell completion sentinel and records exit status/output. With setup script `async:false`, it waits for exit before dispatching the agent; otherwise setup and agent can overlap. A failed setup stage still preserves the worktree and can continue to the agent, so a bot requiring successful dependencies must explicitly inspect setup status. Sources: [setup completion observation](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/ws.ts#L1215), [best-effort failure and async waiting](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/ws.ts#L1303), [completion contract](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/project/ProjectSetupScriptRunner.ts#L26), [async default](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/project/ProjectSetupScriptRunner.ts#L418).

Subscriptions support snapshot-first reads or resume from `afterSequence`. Persist the latest sequence, replace state when a fallback snapshot arrives, and deduplicate events. Request `requestCompletionMarker:true` to know catch-up has finished. These mechanisms remove a race between loading a snapshot and subscribing. Sources: [shell resume](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/packages/contracts/src/orchestration.ts#L990), [thread resume and snapshot fallback](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/packages/contracts/src/orchestration.ts#L1008).

## Authorization and client packaging

Non-browser clients can exchange a bootstrap credential at `POST /oauth/token` for an environment bearer token, then obtain a socket ticket at `POST /api/auth/websocket-ticket` and connect to `/ws?wsTicket=...`. Default bearer session lifetime is 30 days; socket tickets last five minutes. DPoP-bound exchanges use a one-hour session lifetime. The bootstrap exchange consumes ordinary pairing credentials, so this is not a permanent API key or a general OAuth client-credentials flow. Sources: [HTTP auth endpoints](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/packages/contracts/src/environmentHttp.ts#L433), [bootstrap consumption and exchange](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/auth/EnvironmentAuth.ts#L785), [default lifetimes](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/auth/SessionStore.ts#L423), [DPoP lifetime](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/auth/EnvironmentAuth.ts#L821).

The operations require `orchestration:operate`; shell/thread, clone-progress, and setup-progress subscriptions require `orchestration:read`. Terminal APIs separately require `terminal:operate` if the bot needs raw terminal access. These scopes authorize broad environment operations, not one repository. Projects are organizational boundaries rather than filesystem sandboxes; `orchestration:read` includes readable absolute paths outside projects. Treat this as one trusted environment, or isolate the bot host/account. Source: [filesystem boundary](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/docs/internals/environment-auth.md#L59). Sources: [dispatch and subscriptions](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/auth/RpcAuthorization.ts#L25), [clone scopes](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/auth/RpcAuthorization.ts#L107), [setup scopes](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/auth/RpcAuthorization.ts#L129), [terminal scopes](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/apps/server/src/auth/RpcAuthorization.ts#L145).

The repo supplies typed client building blocks in `@t3tools/contracts` and `@t3tools/client-runtime`, but both package manifests mark them private. The RPC protocol uses Effect `RpcClient.make(WsRpcGroup)`. There is no published bot SDK established by these sources. A small adapter pinned to the same upstream revision is the practical recommendation; HTTP dispatch can cover commands, while clone/worktree operations and subscriptions use the typed WebSocket group. Sources: [private contracts package](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/packages/contracts/package.json#L2), [private client runtime](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/packages/client-runtime/package.json#L2), [typed RPC factory](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/packages/client-runtime/src/rpc/protocol.ts#L1), [clone RPC registrations](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/packages/contracts/src/rpc.ts#L935).

## Integration work outside these APIs

Linear provides an agent integration for this trigger: OAuth with `actor=app` and `app:mentionable`, plus Agent session event webhooks. `AgentSessionEvent` with action `created` covers mentions and delegation; `prompted` delivers follow-up prompts. Its `promptContext` supplies issue and comment context. The webhook receiver must respond within five seconds; for a created session, emit an activity and update its external URL within ten seconds. Sources: [Linear agent setup](https://linear.app/developers/agents), [Linear agent interaction](https://linear.app/developers/agent-interaction). Discord mention and channel-history behavior was not verified against first-party docs in this investigation because those documentation requests returned HTTP 403.

The bot must receive and verify mentions/webhooks, fetch the relevant Discord thread/channel or Linear ticket, gather selected GitHub context, decide repository/project routing, and construct the agent prompt. Pass collected text and source URLs in `message.text`; attachments/context have existing schemas and should only be used after decoding against them. The server's turn contract accepts supplied content, not a Discord/Linear mention reference that it resolves on the bot's behalf. This is the recommended division of work. Source: [message contract](https://github.com/pingdotgg/t3code/blob/5cc99e1c23980d7995a13c47f969b47cb68ed1be/packages/contracts/src/orchestration.ts#L1341).
